# AWS Object-Log DynamoDB + S3 ThreadStore Implementation Spec

## Objective

Implement a remote/shared Codex `ThreadStore` backend using DynamoDB as the durable ordering, metadata, and idempotency authority, with S3 as immutable payload storage for rollout batches, snapshots, and compacted history segments.

The backend must allow one Codex process to be destroyed and another Codex process, possibly on another machine, to resume the same thread from durable state without relying on local rollout files.

## Scope

In scope:

- A new AWS object-log DynamoDB + S3 `ThreadStore` implementation.
- Ordered per-thread append of canonical rollout history.
- Retry-safe append idempotency.
- Read-after-commit semantics for `flush_thread`, `load_history`, and `read_thread`.
- Metadata projection for list/read/search filters currently represented by `ThreadMetadataPatch`.
- Tenant/user authorization boundaries through store configuration and storage namespaces.
- External single-active ownership assumption: another layer ensures only one Codex process is active for a thread at a time.
- Import/reconstruction from existing local rollout history.
- Snapshot and compaction hooks for long threads.
- Integration tests for correctness under retries, failed writes, external-owner invariant violations, and resume.

Out of scope for the first version:

- A full DynamoDB item-per-rollout-item backend.
- Full-text search over all rollout payload content.
- Multi-region active/active writes.
- Codex-managed leases, lease renewal, lease stealing, or writer fencing. Split-brain prevention is handled externally.
- A heavy hosted control plane. The first implementation should support direct AWS access from the deployment environment through scoped IAM.
- Changing the higher-level metadata observation semantics. Store implementations should persist explicit metadata patches rather than infer metadata independently.

## Existing Code Boundaries

Current relevant interfaces live in `codex-rs/thread-store`:

- `ThreadStore` defines storage-neutral operations in `codex-rs/thread-store/src/store.rs`.
- `AppendThreadItemsParams` appends ordered `RolloutItem` batches in `codex-rs/thread-store/src/types.rs`.
- `LiveThread::append_items` applies rollout persistence policy, calls `ThreadStore::append_items`, then applies metadata patches through `ThreadStore::update_thread_metadata`.
- `ThreadMetadataPatch` is the explicit metadata update shape for thread discovery/listing fields.
- `RolloutRecorder` in `codex-rs/rollout` remains the local JSONL implementation and compatibility source for imported legacy histories.

The remote backend should preserve this shape:

- Raw history append remains history-only.
- Metadata updates remain explicit patch operations.
- `load_history` reconstructs replayable `RolloutItem` order without exposing local file paths.
- `list_threads`, `search_threads`, `list_turns`, and `list_items` are store-owned projections, not requirements to inline every rollout item in DynamoDB.

## Requirements

### Functional Requirements

1. Create a new thread record with durable metadata, thread identity, and history mode.
2. Resume an existing thread after the external owner has made this Codex process active.
3. Append a batch of ordered `RolloutItem`s to a live thread.
4. Make append retry-safe through stable idempotency keys generated by the adapter or supplied by a caller with its own retry boundary.
5. Guarantee read-after-successful-append for `load_history`, `read_thread(include_history=true)`, and `flush_thread`.
6. Apply `ThreadMetadataPatch` updates without allowing metadata projection to advance beyond committed history.
7. List active or archived threads within the configured tenant/user namespace and supported sort/filter fields.
8. Support search over metadata/title/preview fields in v1. Full rollout-content search requires a later dedicated index.
9. Archive, unarchive, and delete threads using metadata flags and optional payload lifecycle policy.
10. Reconstruct a thread after process or machine loss by reading committed DynamoDB commit records and referenced S3 payloads.
11. Support large payloads by storing serialized batches in S3 rather than DynamoDB.
12. Support snapshots and compaction so long-thread resume does not require unbounded S3 GETs.
13. Support import from existing local rollout JSONL history.

### Correctness Requirements

1. Per-thread history order is defined by monotonically increasing sequence numbers committed in DynamoDB.
2. A committed append is visible only after the DynamoDB transaction succeeds.
3. S3 payloads not referenced by committed DynamoDB records are ignored by readers.
4. Retrying the same idempotency key with the same request hash returns the original committed sequence range.
5. Retrying the same idempotency key with a different request hash fails with an idempotency conflict.
6. Codex relies on an external owner to ensure only one process appends to a live thread.
7. The append path may condition on the expected head sequence to detect an external-owner invariant violation.
8. If an unexpected concurrent append is detected, the backend should fail closed instead of automatically merging two live streams.
9. Metadata projection updates that are derived from append observation should be associated with a committed sequence number.
10. `load_history` must use committed commit records, not eventually consistent list/search projections.

### Performance Requirements

1. Normal append path should use one S3 PUT and one DynamoDB transaction per persisted batch.
2. Append batches should be sized to avoid excessive S3 object count while staying below memory and latency limits.
3. `load_history` should use snapshot plus tail commits when available.
4. Resume of a long thread should be bounded by a configured maximum number of S3 GETs after compaction.
5. List APIs should avoid scanning per-thread commit history.
6. Search v1 should query metadata projections only; content search must be explicitly backed by a later search index.

## Constraints

- DynamoDB items must not contain large rollout payloads; use S3 for serialized batch bodies.
- DynamoDB is the source of truth for committed sequence ranges, idempotency records, and metadata projection.
- S3 object writes happen before the DynamoDB commit and may be orphaned.
- Readers must never discover history by listing S3.
- The implementation must work inside a customer AWS account with minimal operational footprint: DynamoDB table, S3 bucket, IAM policy, KMS keys, CloudWatch metrics/alarms, and optional lifecycle rules.
- Do not require a continuously running service for correctness.
- Do not depend on DynamoDB global secondary indexes for strongly consistent `load_history`; use the base table partition for committed thread history.
- Keep the first implementation to one remote backend. Design interfaces so a later full or SQL backend can be added without changing Codex call sites.

## Architecture

### Components

1. `AwsObjectLogThreadStore`
   - Implements `ThreadStore`.
   - Maps storage-neutral thread-store calls to DynamoDB and S3 operations.
   - Owns serialization, compression, idempotency, snapshots, and projections.

2. DynamoDB table
   - Stores thread head, commit pointers, idempotency records, metadata projections, snapshot pointers, and import state.
   - Uses the configured tenant namespace and thread identity in keys.

3. S3 bucket
   - Stores immutable compressed payload objects for append batches.
   - Stores immutable compressed snapshot and compacted segment objects.
   - Uses lifecycle rules to clean orphaned staging payloads and aged deleted payloads.

4. Optional reconciler task
   - Cleans orphan S3 payloads.
   - Builds snapshots and compacts old commit payloads.
   - Repairs metadata/list projections from committed history when needed.

### DynamoDB Key Model

Single-table layout:

```text
pk = TENANT#{tenant_id}#THREAD#{thread_id}
sk = HEAD
sk = COMMIT#{start_seq_padded}
sk = IDEMP#{operation}#{idempotency_key}
sk = SNAPSHOT#{snapshot_seq_padded}
sk = IMPORT#{import_id}
```

List projection layout can either use a second table or same table with alternate partition keys:

```text
pk = TENANT#{tenant_id}#USER#{user_id}#ACTIVE
sk = UPDATED#{updated_at}#THREAD#{thread_id}

pk = TENANT#{tenant_id}#USER#{user_id}#ARCHIVED
sk = UPDATED#{updated_at}#THREAD#{thread_id}
```

Required GSIs:

- `GSI_UserUpdated`: active or archived threads in the configured namespace sorted by update time.
- `GSI_UserCreated`: active or archived threads in the configured namespace sorted by creation time.
- Optional `GSI_Relation`: parent/descendant listing if relation filters must be efficient.

The base table partition for `TENANT#...#THREAD#...` remains the strongly consistent source for thread head and commit history.

### S3 Key Model

```text
s3://{bucket}/tenants/{tenant_id}/threads/{thread_id}/commits/{start_seq}-{end_seq}-{commit_id}.json.zst
s3://{bucket}/tenants/{tenant_id}/threads/{thread_id}/snapshots/{seq}-{snapshot_id}.json.zst
s3://{bucket}/tenants/{tenant_id}/threads/{thread_id}/segments/{start_seq}-{end_seq}-{segment_id}.json.zst
s3://{bucket}/tenants/{tenant_id}/threads/{thread_id}/imports/{import_id}.json.zst
```

S3 objects are immutable. Use conditional object creation where available. Object metadata should include:

- tenant id
- thread id
- commit id
- sequence range
- payload hash
- schema version

## API Semantics

### Call Context Model

The remote backend should not require every correctness field to be supplied by
every `ThreadStore` method call. The fields belong at different layers:

- Store configuration:
  - AWS table, bucket, region, key prefix, compression settings, snapshot thresholds.
  - Fixed tenant/user namespace for the server deployment.
- Live thread context:
  - Last committed sequence observed by this process.
  - Optional external owner token for diagnostics only, if the external coordinator exposes one.
- Per-operation inputs:
  - The logical operation payload, such as `CreateThreadParams`, `ResumeThreadParams`,
    `AppendThreadItemsParams`, or `ThreadMetadataPatch`.
  - Idempotency key when the caller has a stable retry boundary.
  - Optional expected next sequence for defensive compare-and-append checks.
- Per-operation outputs:
  - Append commit range: `first_seq`, `last_seq`, and committed item count.
  - Idempotent replay flag when the operation returned a previously committed result.

This means the public Codex-facing API can stay close to the current
`ThreadStore` trait. A remote adapter can bind tenant/user namespace when it is
constructed, track the last committed sequence when `create_thread` or
`resume_thread` opens a live thread, and generate append idempotency keys
internally when the caller does not provide one.

The storage protocol still needs these values because DynamoDB conditions need
to validate authorization, idempotency, and ordering. They do not all need to be
explicit arguments on every high-level method.

### create_thread

Input:

- tenant/user namespace from store context
- `CreateThreadParams`
- idempotency key generated by the adapter unless supplied by the caller

Behavior:

1. Put initial S3 payload only if the create operation includes initial canonical history.
2. TransactWrite:
   - conditionally create `HEAD`
   - conditionally create create-idempotency item
   - create active list projection item
3. Return success if the idempotency record already exists with the same request hash.

### resume_thread

Input:

- tenant/user namespace from store context
- `ResumeThreadParams`
- external active-owner guarantee has already been established before this call

Behavior:

1. Strongly read `HEAD`.
2. Verify the thread belongs to the configured tenant/user namespace.
3. Initialize local live-thread context with the current `head_seq`.
4. Return without writing lease state.

### append_items

Current public input:

- `AppendThreadItemsParams`

Remote adapter context:

- tenant/user namespace from store context
- optional idempotency key generated by the adapter or supplied by a future caller
- optional expected next sequence from live thread state, if compare-and-append is enabled

Internal append result:

- `first_seq`
- `last_seq`
- committed item count
- commit id
- idempotent replay flag

Behavior:

1. Canonicalize and serialize the item batch.
2. Compute request hash and payload hash.
3. Strongly read `IDEMP#append#{key}`.
4. If present with matching hash, return the stored commit range.
5. If present with different hash, fail with idempotency conflict.
6. Strongly read `HEAD`.
7. Verify the configured namespace, not deleted, and archive eligibility.
8. Allocate `start_seq = head_seq + 1`, `end_seq = head_seq + item_count`.
9. PUT immutable S3 payload.
10. TransactWrite:
    - condition `HEAD.head_seq` is unchanged
    - condition idempotency item does not exist
    - put commit pointer item
    - put idempotency item
    - update `HEAD.head_seq`, `updated_at`, and optional projection fields
    - update list projection
11. If transaction outcome is unknown because of timeout, strongly read the idempotency item.
12. If transaction failed after S3 PUT, leave the S3 object orphaned for cleanup.

The existing trait currently returns `()`. The AWS object-log backend can initially keep
that public shape and store the append result in the live thread context for
`flush_thread`, telemetry, and metadata sync. If later callers need precise
commit barriers or compare-and-append feedback, introduce an additive
lower-level remote API that returns the append result without forcing all local
store implementations to expose sequence numbers.

### flush_thread

Behavior:

- For direct remote writes, append success is the commit barrier.
- `flush_thread` should verify that all queued local writes have completed.
- It may strongly read `HEAD` and return once the caller's last known commit range is visible.

### load_history

Behavior:

1. Strongly read `HEAD`.
2. If a snapshot is present and allowed, GET latest snapshot payload.
3. Query committed `COMMIT#...` rows after the snapshot sequence.
4. GET referenced S3 payloads in bounded parallelism.
5. Verify payload hashes and sequence ranges.
6. Return ordered `RolloutItem`s.

### read_thread

Behavior:

- Strongly read `HEAD`.
- Return metadata projection.
- If `include_history`, use the same algorithm as `load_history`.

### list_threads

Behavior:

- Query the configured namespace list projection by active or archived partition and sort key.
- Apply filters that are represented in projection attributes.
- Return opaque cursors based on projection key.
- Projection consistency may lag only if a background projection path is introduced. For v1, projection updates should be part of the same DynamoDB transaction as metadata updates where possible.

### search_threads

Behavior:

- V1 supports metadata search over title, preview, name, and similar projected fields.
- DynamoDB does not provide native full-text search. For content search, add a later external index or a deliberately limited token projection.
- `search_threads` should report unsupported or degraded mode if the requested search cannot be served from projections.

### update_thread_metadata

Behavior:

1. Strongly read `HEAD`.
2. Verify the thread belongs to the configured tenant/user namespace.
3. Apply the literal `ThreadMetadataPatch`.
4. Update `HEAD.metadata_version`.
5. Update list/search projections in the same transaction when the affected fields are projected.
6. Do not mutate committed history.

### archive_thread / unarchive_thread / delete_thread

Behavior:

- Archive sets `archived_at`, moves list projection from active to archived, and keeps commit history readable when `include_archived` is true.
- Unarchive clears `archived_at` and moves list projection back to active.
- Delete sets `deleted_at`, removes list projections, and optionally writes a deletion marker for payload lifecycle.
- Hard-delete of S3 objects should be asynchronous and retention-aware.

## External Single-Active Ownership Model

The AWS object-log backend assumes an external coordinator is responsible for ensuring
that only one Codex process is active for a thread at a time. Examples could
include an environment/session scheduler, a durable work allocator, or another
service that owns process lifecycle.

The remote `ThreadStore` should not implement lease acquire, renew, release, or
steal operations in v1.

Rules:

1. `create_thread` and `resume_thread` open local live-thread context only after the external owner has activated this Codex process.
2. The store tracks the last committed sequence observed by this process.
3. Append transactions may condition on `HEAD.head_seq == expected_previous_seq` to detect unexpected concurrent mutation.
4. If the expected sequence condition fails and no matching idempotency record exists, return a concurrency/invariant error rather than retrying into the new head automatically.
5. This defensive check detects accidental split-brain but does not by itself provide fencing. Correctness depends on the external owner maintaining the single-active invariant.
6. Because Codex does not own leases, there is no lease expiry, clock-skew handling, renewal loop, or stale-writer steal path in the ThreadStore backend.

## Idempotency Model

Idempotency key scope:

```text
tenant_id + thread_id + operation + idempotency_key
```

Append idempotency stores:

- request hash
- commit id
- sequence range
- payload hash
- created timestamp
- TTL expiration

Retry behavior:

- Same key and same hash returns previous success.
- Same key and different hash fails.
- Timeout after commit is recovered by reading the idempotency record.
- Timeout before commit leaves no idempotency record; retry attempts a new commit.
- S3 orphan payloads are safe because committed history is discovered only through DynamoDB.

## Snapshot and Compaction Strategy

Initial implementation:

- Append commit payloads as immutable S3 objects.
- Add config thresholds for snapshot eligibility:
  - max commits since last snapshot
  - max bytes since last snapshot
  - max S3 GETs allowed during resume before snapshot warning

Snapshot object:

- Contains replayable `RolloutItem`s through `snapshot_seq`.
- Has a DynamoDB `SNAPSHOT#{seq}` pointer.
- Does not delete original commits immediately.

Compaction:

- Merge older commit payloads into segment objects.
- Write segment pointer records.
- Mark covered commit pointer records as compacted only after the segment pointer commits.
- Readers can prefer segments/snapshots but must still tolerate uncompacted commits.

## Migration and Import

Import from existing local rollout history:

1. Read local rollout history using existing rollout parsing.
2. Create remote thread with original thread id, session id, history mode, and metadata when available.
3. Chunk rollout items into commit-sized batches.
4. Write commit payloads and DynamoDB commit pointers in order.
5. Preserve source timestamps where available.
6. Write metadata projection.
7. Verify `load_history` returns the same ordered rollout items.

Compatibility rules:

- Imported histories should not require local rollout paths after import.
- Local rollout files may remain as backup unless the caller explicitly deletes them.
- Imported sequence numbers start at 1 and preserve replay order.

## Operational Model

AWS resources:

- DynamoDB table for thread store.
- S3 bucket for payloads.
- KMS key or customer-managed keys for encryption.
- IAM policy scoped by tenant/customer deployment.
- CloudWatch metrics and alarms.
- S3 lifecycle rule for orphan staging payloads and deleted thread retention.

IAM permissions:

- DynamoDB: `GetItem`, `PutItem`, `UpdateItem`, `DeleteItem`, `Query`, `TransactWriteItems`.
- S3: `PutObject`, `GetObject`, optional `DeleteObject`, optional lifecycle management.
- KMS: decrypt/encrypt for the table and bucket keys.

Monitoring:

- append latency
- S3 PUT/GET latency and errors
- DynamoDB transaction conflicts
- unexpected head-sequence conflict rate
- idempotency conflict rate
- orphan payload cleanup count
- load_history S3 GET count
- snapshot age and compaction backlog

## Implementation Steps

1. Define remote store configuration.
   - table name
   - bucket name
   - key prefix
   - region
   - tenant resolver
   - append batch size thresholds
   - snapshot thresholds

2. Add storage model types.
   - DynamoDB head item
   - commit pointer item
   - idempotency item
   - list projection item
   - snapshot pointer item
   - S3 commit payload schema
   - S3 snapshot payload schema

3. Implement serialization and hashing.
   - serialize `RolloutItem` batches
   - compress payloads
   - compute request hash
   - compute payload hash
   - validate sequence ranges on read

4. Implement create/resume live-thread context.
   - create head item
   - initialize last observed sequence
   - verify configured namespace
   - rely on external owner for active-process exclusivity

5. Implement append path.
   - idempotency read
   - S3 payload PUT
   - DynamoDB transaction
   - timeout recovery by idempotency read
   - conflict mapping to `ThreadStoreError`

6. Implement read path.
   - `load_history`
   - `read_thread`
   - payload fetch parallelism
   - payload hash validation
   - snapshot plus tail replay

7. Implement metadata path.
   - apply `ThreadMetadataPatch`
   - update head metadata
   - update list projection
   - archive/unarchive/delete state transitions

8. Implement list/search v1.
   - list active/archived threads by projected attributes
   - metadata-only search
   - clear unsupported behavior for full content search

9. Implement import tool or API.
   - local rollout to remote thread
   - verification mode
   - dry-run mode

10. Implement background maintenance.
    - orphan S3 cleanup
    - snapshot creation
    - segment compaction
    - projection repair

11. Add integration tests.
    - local DynamoDB/S3 emulation where practical
    - trait-level conformance suite shared with in-memory/local stores
    - fault injection around S3 PUT and DynamoDB transaction boundaries

12. Add deployment documentation for customer AWS accounts.
    - CloudFormation/Terraform sketch
    - IAM policy
    - lifecycle policy
    - alarms
    - local development setup

## Test Plan

Correctness tests:

- Create then read thread.
- Append one batch and load exact history.
- Append multiple batches and verify sequence order.
- Retry append after simulated timeout and verify exactly one logical commit.
- Reuse idempotency key with different payload and verify conflict.
- Fail after S3 PUT but before DynamoDB transaction and verify no history is visible.
- Fail after DynamoDB commit but before response and verify retry returns same commit range.
- Unexpected concurrent append changes `head_seq` and the stale local process receives an invariant error.
- The backend does not provide fencing if the external single-active owner fails and writers append sequentially without overlapping head checks.
- Metadata update does not create history.
- Metadata list projection changes atomically with metadata update.
- Archive hides thread from active list but allows read with include_archived.
- Delete hides thread and prevents normal resume.
- Import local rollout and compare full replay history.
- Snapshot replay equals full commit replay.
- Compacted segment replay equals original commit replay.

Performance tests:

- Append latency under representative batch sizes.
- Resume latency for short, medium, and long threads.
- Resume latency before and after snapshot.
- S3 GET count during `load_history`.
- DynamoDB transaction conflict behavior under unexpected concurrent append attempts.
- List pagination latency with many projected threads.

Operational tests:

- IAM policy denies cross-tenant reads.
- KMS-encrypted payloads read/write successfully.
- Orphan cleanup ignores committed payloads.
- Lifecycle policy does not remove committed payloads before retention.

## Success Criteria

Implementation is ready when:

1. `AwsObjectLogThreadStore` passes a shared `ThreadStore` conformance test suite.
2. A thread can be created, appended, flushed, shut down, and resumed from a separate process with no local rollout dependency.
3. Retried appends are exactly-once logically under timeout and retry scenarios.
4. Unexpected concurrent head changes are detected and reported as invariant errors.
5. `load_history` returns ordered committed `RolloutItem`s and never observes orphan S3 payloads.
6. Metadata projection supports existing read/list filters required by app-server callers.
7. Archive, unarchive, and delete behavior is covered by tests.
8. Import from local rollout history round-trips replay order.
9. Long-thread resume is bounded by snapshot/compaction thresholds.
10. Customer-account deployment requires only DynamoDB, S3, IAM, KMS, CloudWatch, and optional scheduled maintenance.

## Open Questions

1. Should the remote store use both tenant and user in storage keys, or is a single configured
   deployment namespace sufficient for customer-account installs?
2. Should callers ever supply stable idempotency keys, or should the remote adapter always generate
   them from live thread state and append batch identity?
3. Should `flush_thread` return a committed sequence number, or should it remain a unit-returning trait method for compatibility?
4. What is the minimum acceptable metadata-search behavior for v1?
5. What snapshot interval gives acceptable resume latency for large real-world Codex histories?
6. Should direct AWS access be the only v1 deployment mode, or should an optional remote service wrapper be defined at the same time?
7. How long should idempotency records be retained?
8. How long should deleted thread payloads remain recoverable?
