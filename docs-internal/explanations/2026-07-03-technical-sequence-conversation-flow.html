Conversation Flow: Create Thread, Send Message, Stream Agent Response

This document maps the v2 app-server conversation lifecycle from the client-visible JSON-RPC API through app-server request processors, core session execution, model streaming, event translation, and durable rollout persistence. It is written for engineers preparing to make broad changes in this area.

1. Executive Map

The conversation feature is the v2 JSON-RPC thread and turn flow: create or resume a thread, submit user input as a turn, run the agent/model/tool loop, persist replayable history, and stream notifications back to subscribed clients. The app-server README describes the visible lifecycle: call thread/start, call turn/start, then keep reading notifications such as turn/started, item/started, item/agentMessage/delta, item/completed, and turn/completed. Evidence: codex-rs/app-server/README.md:77-80, codex-rs/app-server/README.md:1353-1355.

Primary entry pointsthread/start, thread/resume, thread/fork, turn/start, turn/steer, turn/interrupt. Protocol definitions: app-server-protocol/src/protocol/common.rs:476-492, 799-814.
Main componentsTUI/app clients, app-server processors, ThreadStateManager, ThreadManager, CodexThread, core Session, ModelClientSession, ThreadStore.
Main durable stateRollout items plus metadata. Local storage writes canonical JSONL history and uses SQLite as a queryable metadata index when available. thread-store/src/local/mod.rs:45-57.
Main async handoffsJSON-RPC requests, background thread_start_task, core submission queue, core event queue, per-thread listener task, model response stream, tool futures.
Main lifecyclethread/start creates a live core thread and attaches a listener; turn/start queues Op::UserInput; core emits events; app-server converts events into notifications.
Open firstapp-server/src/request_processors/thread_processor.rs, turn_processor.rs, thread_lifecycle.rs, core/src/session/handlers.rs, core/src/session/turn.rs, thread-store/src/live_thread.rs.
Highest-risk invariants Turn IDs are core submission IDs and are UUIDv7; app-server exposes them as public turn IDs. Settings updates and user turns are serialized through the same core submission loop. The per-thread listener must track core events before emitting v2 notifications. Terminal turn events are explicitly flushed after being appended to rollout storage. Evidence: core/src/session/mod.rs:890-897, core/src/session/handlers.rs:702-765, app-server/src/request_processors/thread_lifecycle.rs:311-341, core/src/tasks/mod.rs:799-803.

2. Feature Boundary

In scope: the app-server v2 JSON-RPC APIs for starting/resuming/forking threads and starting/steering/interrupting turns; the app-server process-local thread subscription/listener state; core thread/session execution; model Responses streaming; item and turn notifications; and rollout/thread-store persistence.

Out of scope except where they affect the sequence: realtime conversation APIs, review-specific delivery modes, plugin installation, MCP server startup details, environment management internals, memory jobs, and UI rendering. These systems call into or are called by the conversation flow, but they are not the primary path for “create conversation, send message, get agent response.”

The public API boundary is v2 JSON-RPC. common.rs maps method names to request and response payloads, while notification definitions list the server-initiated stream that clients receive. Evidence: app-server-protocol/src/protocol/common.rs:476-492, 799-814, 1607-1635.

The core boundary is CodexThread: app-server submits Ops to it and reads Events from it. The protocol crate defines Submission, Op::UserInput, and EventMsg as the transport between app-server-facing core handles and the session loop. Evidence: protocol/src/protocol.rs:161-166, 515-545, 1254-1324.

Inbound Callers

  • The TUI starts a thread by sending ClientRequest::ThreadStart with ThreadStartParams derived from config. Evidence: tui/src/app_server_session.rs:461-480, 1402-1432.
  • The TUI sends user input by calling turn_start, which emits ClientRequest::TurnStart with thread_id, input items, cwd, model, effort, permissions, and other overrides. Evidence: tui/src/app_server_session.rs:772-820.
  • Other app-server clients use the same v2 JSON-RPC methods; the README’s examples and method list document that API surface. Evidence: app-server/README.md:140-143, 171, 731-769.

Outbound Dependencies

  • Model Responses API over WebSocket or HTTPS. ModelClientSession::stream tries WebSocket when enabled and falls back to HTTP when required; both paths build a streaming Responses request. Evidence: core/src/client.rs:1728-1777, 1351-1424, 1465-1628.
  • Thread storage through the storage-neutral ThreadStore trait; local implementation writes JSONL rollout history and optional SQLite metadata. Evidence: thread-store/src/store.rs:29-138, thread-store/src/local/mod.rs:45-57.
  • Tools, plugins, MCP tools, dynamic tools, approvals, and environments are reachable during a turn. Tool availability is built in built_tools before each sampling request. Evidence: core/src/session/turn.rs:1177-1305.

6. Async Handoff Inventory

  • JSON-RPC serialization: method definitions attach serialization keys such as thread_id(params.thread_id) for turn methods, so requests for the same thread are serialized before processor execution. Evidence: app-server-protocol/src/protocol/common.rs:799-814.
  • Thread start background task: thread/start is handled by thread_start_task, which loads config, creates core thread, attaches listener, sends response, then sends thread/started. Evidence: app-server/src/request_processors/thread_processor.rs:1050-1317.
  • Core submission queue: Session::spawn_internal creates a bounded submission channel with capacity 512 and an unbounded event channel, then spawns submission_loop. Evidence: core/src/session/mod.rs:538-540, 713-719.
  • Core event queue: app-server reads conversation.next_event() in a per-thread listener task and translates events to notifications. Evidence: app-server/src/request_processors/thread_lifecycle.rs:277-353.
  • Per-thread listener command channel: ThreadState::set_listener creates an unbounded listener command channel; listener commands are handled in the same listener select loop as core events. Evidence: app-server/src/thread_state.rs:101-117; app-server/src/request_processors/thread_lifecycle.rs:285-300.
  • Idle unload watcher: after no subscribers and no activity, the listener triggers unload; README documents a 30 minute delay and code shuts down, removes the thread, and emits thread/closed. Evidence: app-server/README.md:455-478; app-server/src/request_processors/thread_lifecycle.rs:354-385, 407-457.
  • Model stream: try_run_sampling_request awaits stream events; output item completions feed tool execution/history, deltas produce user-visible item deltas, and ResponseEvent::Completed finalizes token usage and sampling result. Evidence: core/src/session/turn.rs:1887-2075, 2100-2260.
  • Tool futures: completed response items can enqueue tool futures in a FuturesOrdered queue; tool output can require follow-up model sampling. Evidence: core/src/session/turn.rs:1926-1928, 2059-2073.
  • Retries and fallback: retryable stream errors sleep with backoff, notify users on later reconnects, and can switch from WebSocket to HTTPS after exhausting retry budget. Evidence: core/src/responses_retry.rs:20-79.
  • Cancellation: stream waits and task runs are tied to cancellation tokens; task abort allows a grace period before aborting and emits TurnAborted. Evidence: core/src/session/turn.rs:1960-1968; core/src/tasks/mod.rs:829-908.

7. Evolutionary History

The implementation carries compatibility surfaces from older storage and API shapes. Local thread storage explicitly treats JSONL rollout files as the durable replay format even when SQLite exists, because old local rollout files and SQLite-less reads must remain supported. Evidence: thread-store/src/local/mod.rs:45-57.

Core protocol events retain v1 wire names for turn lifecycle events: TurnStarted serializes as task_started with alias turn_started, and TurnComplete serializes as task_complete with alias turn_complete. This is a compatibility branch that matters if changing event serialization or replay. Evidence: protocol/src/protocol.rs:1308-1320.

Deprecated and experimental fields coexist in v2 APIs. For example, multiAgentMode is deprecated and ignored in thread/turn parameters, while newer behavior is controlled by reasoning effort; raw response item notifications are internal/experimental and opt-in. Evidence: app-server-protocol/src/protocol/v2/thread.rs:103-112, 143-147; app-server-protocol/src/protocol/v2/turn.rs:154-157; README: app-server/README.md:140-143, 171.

Inference, labeled The code appears to be in an active migration from raw/core event history toward paginated, projected app-server thread history. Evidence includes ThreadHistoryMode, paginated thread/turns/list and thread/items/list, and stored item projections, but this document did not inspect PR discussions. Evidence: thread-store/src/types.rs:332-386; README: app-server/README.md:498-529.

8. Explicit Assumptions

  • Ordering: per-thread JSON-RPC requests are serialized, and core submissions are processed by a single submission_loop. Do not bypass either without rethinking ordering. app-server-protocol/src/protocol/common.rs:799-814; core/src/session/handlers.rs:702-765.
  • One active regular task: spawn_task aborts existing tasks with TurnAbortReason::Replaced before starting a new one. core/src/tasks/mod.rs:313-323.
  • Turn identity stability: callers may rely on UUIDv7 timestamp properties of turn IDs. core/src/session/mod.rs:890-897.
  • Persistence-before-delivery: core appends event/response rollout items before delivering or completing lifecycle notifications, and terminal events get explicit flush barriers. core/src/session/mod.rs:1916-1923, 2774-2791; core/src/tasks/mod.rs:799-803.
  • Listener state synchronization: app-server tracks an event in ThreadState before emitting typed translations, so active-turn snapshots and raw-event opt-in remain in sync. app-server/src/request_processors/thread_lifecycle.rs:311-341; app-server/src/thread_state.rs:144-154.
  • Trust boundary: app-server maps v2 request fields into core configuration and permission settings; clients do not directly mutate core state. app-server/src/request_processors/turn_processor.rs:484-519.
  • Retry semantics: stream retries can replay the same prompt built from history; non-retryable errors terminate the sampling request. core/src/session/turn.rs:1099-1165; core/src/responses_retry.rs:48-79.
  • Restart recovery: loaded ThreadState is ephemeral, but persisted rollout history and metadata can reconstruct API thread/turn state on resume/read. thread-store/src/store.rs:64-92; app-server/src/thread_state.rs:77-91.
  • Version skew: v1 event names and v2 notification projections coexist, so changing event names or item projection shapes can break older replay/client paths. protocol/src/protocol.rs:1308-1320; app-server-protocol/src/protocol/common.rs:1607-1635.

9. End-to-End Sequence

This concrete example follows the TUI starting a thread, sending “Explain this diff,” and receiving the final assistant message.

Step 1: Client creates a thread

The TUI calls ClientRequest::ThreadStart using params derived from config. The request includes model/provider, cwd, workspace roots, approval/sandbox or permissions settings, ephemeral setting, and thread_source: User. Evidence: tui/src/app_server_session.rs:461-480, 1402-1432.

{
  "method": "thread/start",
  "params": {
    "cwd": "/workspaces/codex",
    "model": "gpt-5.1-codex",
    "threadSource": "user"
  }
}

Failure surfaces here include config load errors, invalid dynamic tools, trust persistence failures that are tolerated with in-memory trust, or thread creation errors. Evidence: app-server/src/request_processors/thread_processor.rs:1072-1150, 1195-1200.

Step 2: App-server creates core thread and attaches listener

thread_start_task calls ThreadManager::start_thread_with_options, gets a thread_id, core thread, and session_configured, then builds the API Thread from a config snapshot. Before notifying the client, it auto-attaches the per-thread listener for the requesting connection. Evidence: app-server/src/request_processors/thread_processor.rs:1163-1247.

The app-server sends the JSON-RPC response first and then sends thread/started. Evidence: app-server/src/request_processors/thread_processor.rs:1279-1311.

Step 3: Client submits user input

The TUI calls turn/start with thread_id, input items, and current turn overrides. The processor loads the thread, validates direct input and input size, maps v2 input into core input items, resolves environment/cwd/settings overrides, builds Op::UserInput, and submits it to core. Evidence: tui/src/app_server_session.rs:772-820; app-server/src/request_processors/turn_processor.rs:442-535.

{
  "method": "turn/start",
  "params": {
    "threadId": "thr_123",
    "input": [{ "type": "text", "text": "Explain this diff" }]
  }
}

The response returns immediately with an in-progress Turn and empty items. The real running lifecycle begins later when core emits TurnStarted. Evidence: app-server/src/request_processors/turn_processor.rs:554-568; app-server/README.md:171.

Step 4: Core serializes and starts the turn

submit_user_input_with_client_user_message_id generates a UUIDv7 submission ID and sends a Submission into the bounded channel. The submission loop receives Op::UserInput and calls user_input_or_turn. Evidence: core/src/session/mod.rs:752-768, 890-897; core/src/session/handlers.rs:702-759.

user_input_or_turn_inner applies settings, creates a new turn context, steers input if there is an active turn, or spawns a RegularTask when idle. Evidence: core/src/session/handlers.rs:183-275.

Step 5: Core emits TurnStarted

RegularTask emits EventMsg::TurnStarted inline before the first model call. App-server’s listener receives the event, updates ThreadState, and apply_bespoke_event_handling sends a turn/started notification with a fresh in-progress Turn. Evidence: core/src/tasks/regular.rs:47-58; app-server/src/request_processors/thread_lifecycle.rs:302-341; app-server/src/bespoke_event_handling.rs:155-183.

Step 6: Core builds prompt and streams model output

run_turn records context updates and input, builds skills/plugins/tool routing, clones history into prompt input, builds a Responses request, and calls ModelClientSession::stream. The request is explicitly streaming and contains model, instructions, input, tools, reasoning, service tier, prompt cache key, output schema/text config, and client metadata. Evidence: core/src/session/turn.rs:142-207, 270-294, 1043-1117; core/src/client.rs:812-890.

When WebSocket streaming is enabled, the client tries WebSocket first; otherwise or after fallback it uses HTTP streaming. Evidence: core/src/client.rs:1728-1777.

Step 7: Stream events become rollout items and notifications

As try_run_sampling_request receives ResponseEvents, output item completions are handled, tool calls may enqueue futures, assistant message item starts are emitted, and text deltas become AgentMessageContentDelta events. Evidence: core/src/session/turn.rs:1887-2075, 2100-2260.

Core persists event messages before delivery and persists response items before raw item emission. App-server translates core item events into v2 notifications such as item/started, item/agentMessage/delta, and item/completed. Evidence: core/src/session/mod.rs:1916-1923, 2774-2791; app-server/src/bespoke_event_handling.rs:869-889, 1348-1411.

Step 8: The turn completes

When the stream sends ResponseEvent::Completed, core records token usage and decides whether another sampling request is needed. If no follow-up is needed, the task finishes; on_task_finished emits TurnComplete, clears the active turn when appropriate, and flushes the terminal event. Evidence: core/src/session/turn.rs:2212-2238; core/src/tasks/mod.rs:743-804.

App-server receives TurnComplete, aborts pending per-thread server requests, resolves interrupts, updates watch status, and emits turn/completed with final status/error/timing metadata. Evidence: app-server/src/bespoke_event_handling.rs:185-200, 1348-1369.

10. Code Walkthrough

API contracts

app-server-protocol/src/protocol/common.rs owns method and notification names. v2/thread.rs, v2/turn.rs, and v2/thread_data.rs own request/response/notification payloads. These files matter because API-level changes must preserve wire naming, experimental gates, and optional-field semantics. Evidence: common.rs:476-492, 799-814, 1607-1635; v2/thread.rs:56-201; v2/turn.rs:68-165.

App-server composition

MessageProcessor owns the process-scoped ThreadStore, creates ThreadManager, and wires ThreadRequestProcessor and TurnRequestProcessor. This is the app-server dependency root for the flow. Evidence: app-server/src/message_processor.rs:333-389, 482-512.

Thread lifecycle

thread_processor.rs owns start/resume/fork request handling. For start, thread_start_task loads config, starts core thread, attaches listener, updates watch state, sends response, then notifies thread/started. Evidence: app-server/src/request_processors/thread_processor.rs:1050-1317.

Turn submission

turn_processor.rs maps TurnStartParams to Op::UserInput, submits through CodexThread::submit_user_input_with_client_user_message_id, records request-to-turn correlation, and returns an initial in-progress turn. Evidence: app-server/src/request_processors/turn_processor.rs:442-568.

Listener and event translation

thread_lifecycle.rs starts the per-thread listener and owns the select loop over cancellation, listener commands, core events, and idle unload triggers. bespoke_event_handling.rs maps core EventMsg variants to v2 notifications and server-initiated requests. Evidence: app-server/src/request_processors/thread_lifecycle.rs:138-187, 277-353; app-server/src/bespoke_event_handling.rs:139-200, 869-889.

Core session queue and task lifecycle

core/src/session/mod.rs creates the submission and event channels. handlers.rs serializes ops. tasks/mod.rs enforces the running task lifecycle and terminal flushes. Evidence: core/src/session/mod.rs:538-540, 713-719; core/src/session/handlers.rs:702-765; core/src/tasks/mod.rs:313-451, 743-804.

Model/tool loop

core/src/session/turn.rs owns the agent loop: record inputs, build prompt, build tools, stream model output, run tools, continue sampling if needed, and return the last assistant message. Evidence: core/src/session/turn.rs:128-140, 217-330, 1043-1165, 1887-2260.

Streaming transport

core/src/client.rs owns Responses request construction, WebSocket/HTTP streaming, stream mapping, telemetry, and failure recording. responses_retry.rs owns retry/fallback policy. Evidence: core/src/client.rs:812-890, 1351-1424, 1465-1628, 1867-2036; core/src/responses_retry.rs:20-79.

Persistence

thread-store/src/store.rs defines the storage boundary. live_thread.rs owns active persistence lifecycle and append-derived metadata updates. local/mod.rs defines the local JSONL/SQLite compatibility contract. Evidence: thread-store/src/store.rs:29-138; thread-store/src/live_thread.rs:27-31, 89-187; thread-store/src/local/mod.rs:45-57.

11. Change Guide

  • Start at the API contract if the change affects clients: app-server-protocol/src/protocol/common.rs, v2/thread.rs, v2/turn.rs, and v2/thread_data.rs. Preserve camelCase wire names and experimental gating conventions.
  • For request behavior, change processors first and core second: thread_processor.rs for create/resume/fork, turn_processor.rs for user input and overrides, then core/src/session/handlers.rs for submission semantics.
  • For response generation, inspect core/src/session/turn.rs, core/src/stream_events_utils.rs, and core/src/client.rs. Do not assume one user-visible turn equals one model request.
  • For notification behavior, preserve the listener rule: track event state before emitting v2 translations. Changing notification order can break clients that merge active-turn snapshots with streamed items.
  • For persistence, prefer LiveThread and ThreadStore boundaries. Avoid direct store writes for live sessions unless you also maintain metadata sync and flush barriers.
  • Run protocol tests after API shape changes: just test -p codex-app-server-protocol. Run app-server tests for processor/listener changes. Run core tests for session/model loop changes. If changing common/core/protocol behavior broadly, ask before running the complete just test suite per repo instructions.
  • Useful traces include app_server.thread_start.*, session_loop, turn, stream_request, receiving_stream, and model_client.stream_responses_*. Evidence: app-server/src/request_processors/thread_processor.rs:1190-1310; core/src/session/mod.rs:713-719; core/src/tasks/mod.rs:384-433; core/src/session/turn.rs:1912-1924; core/src/client.rs:1339-1351, 1465-1477.

13. Risks and Edge Cases

  • Partial failure during thread start: live persistence can be opened before session initialization fully succeeds; LiveThreadInitGuard discards the live writer on early return rather than materializing lazy state. thread-store/src/live_thread.rs:40-87.
  • Duplicate or concurrent turn requests: per-thread request serialization and core submission ordering reduce races, but turn/start while a turn is active can become steer input or fail depending on active turn steerability. core/src/session/handlers.rs:220-275; README error section: app-server/README.md:1434.
  • Out-of-order client observations: turn/start response returns before turn/started; clients must treat response as accepted/in-progress, not as evidence that the task has begun. app-server/src/request_processors/turn_processor.rs:554-568; app-server/README.md:171.
  • Stream disconnects: retryable stream errors back off and may emit “Reconnecting...” warnings; exhausting WebSocket retry budget can switch transport to HTTPS. core/src/responses_retry.rs:31-75.
  • Consumer drops stream: mapped response stream records cancellation if the consumer is dropped before provider terminal event. core/src/client.rs:1905-1929.
  • Terminal event durability: terminal turn events need explicit flush after emission because regular items may have been flushed before the terminal event was appended. core/src/tasks/mod.rs:799-803, 903-907.
  • Raw response event leakage: raw response item notifications are internal and gated by experimental_raw_events; listener filters them unless enabled, while still emitting hook prompt items where needed. app-server-protocol/src/protocol/v2/thread.rs:143-147; app-server/src/request_processors/thread_lifecycle.rs:328-339.
  • Loaded-thread unload: once the last subscriber leaves, unload is delayed and only happens when idle; attempts to attach while a thread is closing are rejected. app-server/src/request_processors/thread_lifecycle.rs:156-162, 354-385.
  • Metadata drift: raw store appends are not enough to update metadata; live appends must flow through LiveThread or explicit update_thread_metadata. thread-store/src/local/mod.rs:53-57; thread-store/src/live_thread.rs:169-185.
  • Version skew: clients may consume v1 event names in rollout history while live clients consume v2 notifications; avoid renaming without migration/compatibility. protocol/src/protocol.rs:1308-1320.
